# Techo: project outline

Date: 2026-11-22
Status: agreed in discussion; the input to detailed planning. Nothing here is built yet.

Techo is an online note-taking service: an HTTP API that stores notes as generic nodes,
so that different clients can consume them. The first client will be Emacs, storing org
text, and is a separate project.

## 1. Scope

**In v1**

- One self-hosted instance. One SQLite database, in WAL mode, on a mounted volume.
- Every node is private to its owner.
- JSON over REST.
- Accounts are created by an admin through the CLI.

**Not in v1**

- Sharing between users.
- Attachments (the shape is decided: §8).
- Open signup, email verification, password reset.
- Merging on the server. A conflicting write is rejected, and the client merges.

## 2. Clients

- A client keeps its own files and its own version tracking, and syncs with the API.
  Example: an Emacs client keeps one org file per node.
- The server never interprets a body. Each node carries a `content_type`, such as
  `text/org` or `text/markdown`.

## 3. Domain model

**Node**

| Field | Notes |
|---|---|
| id | UUIDv7, generated by the client, so a create can be retried safely |
| owner, author | the same account in v1; both kept for later sharing |
| kind | one of five, fixed on the server |
| title, body, content_type | body is opaque text |
| props | JSON, validated per kind |
| tags | any node can be tagged |
| parent | one parent per node, or none |
| revision | integer, bumped by every change to the node |
| timestamps | created, updated |

**Kinds**

| Kind | What it is | Props |
|---|---|---|
| Project | a collection of nodes of any kind | none yet |
| Journal | a collection of Notes, shown by time | none yet |
| Note | a general note | a timestamp when its parent is a Journal |
| Task | a todo item | status, deadline, scheduled |
| Contact | a person, business or place | vCard's basics: names, emails, phones, addresses, organisation |

- A Journal entry is a Note whose parent is a Journal. A Journal may hold several
  entries for one day; their timestamps order them.
- Task status is `TODO`, `DONE` or `WONTDO`. `deadline` and `scheduled` are dates, not
  states.

**Structure**

- Containment is a tree: one parent per node. Moving a node changes its parent.
- Links are separate: a typed edge between any two nodes.
- The server stores no order among a Project's children. The client sorts.

## 4. Versioning and sync

- **One revision counter per node.** It is the node's ETag. A content edit, a props
  change and a move all bump it.
- **Writes need `If-Match`.** A stale one is refused with 412, a missing one with 428.
- **Full history.** Every write appends a snapshot (title, body, props, tags) to an
  append-only revisions table. No deltas.
- **Restore** writes a new revision whose content is copied from an old one. History is
  never rewritten.
- **Retention:** keep everything in v1. Purging a trashed node deletes its history.
- **Change feed:** a per-owner sequence orders every change, so a client can ask what
  changed since a cursor. Deletes leave tombstones.
- **Known cost:** an offline body edit conflicts with a move made on another device.
  The client refetches and retries. Accepted for the sake of one ETag per node.

## 5. API

- REST resources: nodes, revisions, links, tags, search, changes, API keys.
- Commands as `POST` sub-resources: move, task transition, trash, restore, key
  regeneration. Each maps to one state machine event.
- Why REST and not JSON-RPC: `If-Match`, `ETag`, 412 and 428 are HTTP's own, and circuit
  is shaped around resources.
- One error format for every refusal.
- Every list is paged, with a cap: nodes, search results, the change feed.

## 6. State machines

Each machine is a transition table in Scheme, with a pure step function
`(step state event) -> state' + effects`.

- Node lifecycle: active, archived, trashed, purged.
- Task status: `TODO`, `DONE`, `WONTDO`.
- API key lifecycle.
- The versioned write: how a write is checked against the node's revision.

Verification, in three layers:

1. **Static checks on the table:** every state reachable, deterministic, no unintended
   dead end. The tables are finite, so these are exhaustive.
2. **Generated diagrams:** rendered from the table, so the documents cannot drift.
3. **Model-based tests:** random event sequences run against the real handlers and
   SQLite, compared with the pure model.

TLA+ is optional, and only for the multi-client conflict protocol.

## 7. Accounts and keys

- An account has a username, an email and a password. An admin creates it with the CLI.
- Login is by email and password. It returns an API key.
- A user has several keys, one per device, each named and revocable. A key is shown
  once and stored hashed. It can be regenerated.
- Passwords are hashed with argon2id, through `chez-sodium`.
- API keys are random and long, so a fast hash is right for them, and ordinary requests
  stay quick.
- Login is rate-limited per email and per address, before any hashing (§9).

## 8. Attachments (deferred)

- An attachment is its own resource, owned by a node. It is not a node kind, so bodies
  stay text and searchable.
- Blobs are content-addressed by SHA-256 and kept in an object store, S3 or one like
  it. Their metadata lives in SQLite.
- Storage sits behind a small interface: a filesystem adapter for tests, an S3 adapter
  for production.
- Clients upload straight to the store through presigned URLs.
- This gives chez-curl a server-side use, and needs HMAC-SHA256 for request signing.

## 9. Architecture

- **Functional core, imperative shell.** Core: validation, state machines, revision
  logic. Shell: circuit handlers, SQLite, the clock, entropy.
- **The server is one thread.** chez-http-server runs one libuv loop, and each request
  is a coroutine on it. A blocking call holds up every request.
- **The database: one connection on the loop's thread, called synchronously.** A
  handler that does not wait inside a transaction cannot be interleaved with another
  request, so each transaction is atomic.
  - One doorway: a handler passes a closure to a single procedure and gets a value
    back. A later worker thread can run the same closure, with no handler changed.
  - Nothing waits inside that closure. A request's body is read first.
  - Database time is logged per request.
- **Password hashing blocks the loop** for the length of one hash. Logins are rare, and
  the rate limit bounds the damage.
- **Later:** a database worker thread and off-loop hashing both need a handler to be
  woken from another thread. chez-http-server has no such thing today:
  [the proposal](briefs/chez-http-server-await-outside.md).

## 10. Operations

- 12-factor: all configuration comes from the environment (database path, port, data
  directory).
- One binary is both the server and the admin CLI: `docker exec techo techo user add`.
- Docker image; the database directory is a mounted volume, with its `-wal` and `-shm`
  files beside it.
- Backup is a CLI command, `VACUUM INTO`, safe while the server runs.
- Migrations run from the CLI.
- Integration tests drive the running server with chez-curl.

## 13. Slices, in rough order

1. Skeleton: Makefile, Akku, the Guix script, CI, a health endpoint. Includes a spike
   that measures how long representative queries hold the loop: a node write with its
   snapshot, a search, a page of the change feed.
2. Schema, migrations, the CLI's migrate command.
   - 2b. The database doorway: the write and read workers (ADR-0008, amended
     2026-11-23).
3. Accounts, `techo user add`, login, API keys.
4. Node create, read, update, with revisions and `If-Match`.
5. The tree and move; then links.
6. Kinds and their props; task transitions.
7. Tags and search.
8. The change feed.
9. The Docker image and backup.
